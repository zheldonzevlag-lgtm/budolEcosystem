Payment Lifecycle – Next Phase Improvements

1

Implement CRON Job: Auto-expire stale PENDING transactions

Any Transaction in PENDING status for more than 30 minutes should be automatically set to CANCELLED with reason = "Session expired (auto-cleanup)". This handles browser crashes, lost connections, and any other edge cases where the explicit cancel call did not complete.

Priority: HIGH
2

Add updatedAt field to Transaction model

The Transaction schema currently has createdAt and completedAt but no updatedAt. Adding it would allow the CRON cleanup job to precisely identify transactions that have been idle for > 30 minutes, and improve audit trail accuracy.

Priority: HIGH
3

Set PAYMENT_GATEWAY_URL in Vercel (budolshap project)

The cancel proxy in budolshap falls back to localhost:8004 when this env var is missing. In production, all cancel calls will silently fail until this is set. Risk R-005 in the risk register.

Priority: HIGH (pre-deploy blocker)
4

Unify PaymentIntent identifiers across the adapter layer

The budolpay-adapter previously conflated referenceId (JON-xxx) and paymentIntentId (UUID) into a single field, causing the cancel flow to send null to the gateway. A formal ValueObject or DTO for payment identities would prevent this class of bug in future adapters.

Priority: MEDIUM
5

Add Jest integration tests to CI pipeline

The cancel test suite in scripts/test_scripts/payment_gateway/cancel.test.js must run automatically on every pull request targeting main. This prevents regression of the PENDING→CANCELLED lifecycle fix.

Priority: MEDIUM
6

Show real-time transaction status update in Admin Dashboard

The gateway cancel endpoint already calls notifyAdmin('transaction_cancelled', ...). The Admin Dashboard should subscribe to this event and update the transaction row's status badge without requiring a page refresh.

Priority: MEDIUM
7

Expose a "Void / Manual Cancel" button in the Admin Dashboard transactions table

For cases where a transaction is stuck in PENDING due to a gateway communication failure, administrators should be able to manually trigger a cancel via the Admin UI, which calls the new POST /cancel/:referenceId endpoint.

Priority: LOW
